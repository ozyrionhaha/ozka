# Reproducible benchmark suite

Run `npm ci`, `npm run build`, `npm run demo`, then `npm run bench`. Node runs with `--expose-gc`. OpenSSL generates a one-day, loopback-only test certificate under ignored `work/bench-tls`; it is not a bot credential or production certificate. On Windows the script defaults to Git's bundled OpenSSL; set `OPENSSL_BIN` to override. On Linux/macOS it uses `openssl` from PATH. Only spawned benchmark workers trust the test CA via `NODE_EXTRA_CA_CERTS`; TLS verification is not disabled.

The lockfile pins Node dependencies. Runtime version, OS, CPU, architecture, logical cores, RAM, timestamps, rounds and individual samples are written to `results/latest.json`. `RESULTS.md` is generated from these values. Set `BENCH_REPETITIONS` for more rounds (default 3). Worker processes run sequentially; library order rotates across rounds. Close other CPU-heavy programs and run many rounds before drawing conclusions.

## Workloads

- **Startup:** dynamic import plus empty client construction inside a fresh Node process. It excludes process launch and intentionally uses the OS's ordinary, often warm file cache. All adapters use zero Gateway intents, no login and disabled message caching. Idle heap/RSS are measured after a 50 ms settling period and forced GC; baseline heap delta is retained.
- **Dispatch:** three identical listeners, 20,000 warmup events, ten blocks of 200,000 public emits. Each listener increments the same sink. Block ns/event, p50/p95 and CPU user/system microseconds are stored. A percentile across block averages is not an individual event tail latency.
- **Synthetic Gateway baseline:** parse the same JSON packet and emit its data through each public emitter 10,000 times. Individual p50/p95/p99 samples include clock overhead. These are explicitly **not** competitors' internal Gateway pipelines, hydration, caches or socket processing. Ozka's actual `Gateway.receive(JSON.parse(...))` also runs separately for 100,000 packets and has no competitor ranking.
- **Allocations:** V8's sampling heap profiler estimates heap bytes during a separate 50,000-event parse/emit run. Collected minor/major objects are included; samples and estimated bytes are preserved. These are statistical estimates, not exact allocation counts, retained heap or native memory. Profiler timing is excluded from throughput timing.
- **CPU:** `process.cpuUsage()` deltas for emit and REST work. Microseconds include user and system time. These are process CPU durations, not whole-machine utilization percentages.
- **Caches:** 200,000 deterministic seeded lookups/inserts at capacity 1,000, with an 80/20 hot/cold key generator. Ozka uses its LRU; other adapters use their Map-compatible Collection with the identical LRU policy applied externally. All store the same plain `{ id }` values, without entity construction. Compare hits and bounded size as well as time; this is a container/policy microbenchmark, not a model of competitors' default entity caches.
- **REST:** twenty warmups plus 200 sequential GETs against the same local HTTPS server, returning identical JSON and large, non-blocking rate-limit headers. Uses each library's request API. Ozka uses its default Node transport; discord.js uses its bundled REST manager; Oceanic uses its request manager. Eris only accepts an HTTPS host on the default port, so a keep-alive Agent redirects its TCP connection to the loopback port while retaining TLS verification. This includes local TCP/TLS, parser, scheduler and server work; network latency is not subtracted. It is not pure wrapper overhead or a live Discord rate-limit test.
- **UI:** five warmups plus thirty renders of the same 1100×680 showcase with the bundled font and avatar. PNG encoding and layout are included. The native backend is shared across frames. Other libraries have no equivalent built-in free-position renderer, so no competitor number is fabricated.
- **Large simulation:** `npm run bench:stress` replays one million synthetic events through eight in-process receivers and bounded caches, then makes 20,000 mock REST calls across high-cardinality channel IDs. It records memory samples, CPU, event-loop delay and elapsed time. It is Ozka-only, has no real socket/API traffic and is not a production soak test.

## Initial bottleneck and improvement

The initial benchmark used Node's global fetch as Ozka's default REST transport. Its local p95 was about 16 ms on this host; see the archived `results/initial-fetch-transport.json`. Replacing the default with a buffered Node HTTP/HTTPS transport reduced that workload's p95 substantially in the subsequent measurement. This is an observed transport/environment effect, not proof of a universal improvement or explanation of every underlying scheduler cost. Global fetch remains injectable. The revised Node transport also bounds response bytes.

Native graphics use existing Skia bindings. The suite does not contain a JavaScript-vs-Rust or native-vs-WASM rasterizer comparison, so it makes no claims about those relative speeds. No additional Rust/WASM networking/parser package was introduced without evidence of a relevant bottleneck.

The large simulation also exposed unnecessary promise allocation on ordinary Gateway dispatches. The event path now runs synchronously until it encounters event middleware or interaction routing. `results/stress-before-dispatch-optimization.json` and `results/stress.json` retain the observed before/after timings, CPU and peak memory for the same workload. Those single-run differences are diagnostics, not a broad statistical performance claim. The stress loop deliberately yields between batches of 10,000 packets; its event-loop delay reflects that burst size as well as the library work.

## Limits

All tests are local simulations or loopback. There are no live Discord credentials, server-scale fleet tests, compressed Gateway benchmarks, production cache distributions, voice workloads or cross-machine results. Startup feature sets and idle caches differ. Three rounds provide a smoke baseline with substantial potential noise. Read the raw samples and report regressions with the lockfile, runtime and machine context. Do not turn one column into an overall “faster than” claim.
